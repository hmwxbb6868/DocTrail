# DocTrail 接口契约

## 单一事实来源

- `contracts/public-openapi.yaml`：浏览器到 Java 的 HTTP/JSON v1 契约。
- `contracts/ai-openapi.yaml`：Java 到 Python 的内部 HTTP/JSON 契约。
- `contracts/sse-events.yaml`：SSE 事件名称、字段、顺序和结束规则。
- `contracts/examples/`：契约引用的可解析样例。

实现与生成文档不得反向覆盖上述文件。字段或路径变化必须先修改契约，再同步 Java、Python、前端、样例和测试。

## 当前接口概览

- 用户端通过 Java 公共 API 登录、管理会话、发送问答和查看知识库。管理端负责文档管理、仪表盘和 Agent 运行记录。
- `GET /api/admin/dashboard` 返回真实数据库统计。累计成功率只计算成功和失败的运行，`finishedRunCount` 用于区分暂无样本和 `0%`。
- 文档上传返回 `202` 后异步解析。本地 Compose 使用共享卷保存上传文件，内部接口以 `storage_key` 标识文件。
- 问答采用同步 HTTP。保留的流式兼容入口返回 `501`，不提供流式生成。

详细字段和错误语义以本仓库的 OpenAPI 文件为准。以下阶段记录用于回溯接口演进。

## 当前主路线与阶段 5/6 契约边界

- 阶段 6 才创建 Agent 审计三表并把同步 `execution_trace` 落库。内部字段使用 snake_case，公共字段使用 camelCase；`steps`/`tool_calls` 允许空数组，Trace 对象拒绝未知字段。
- 阶段 6 / 切片 5 在既有同步 `POST /api/ask` 内增加保守 Router/ChitChat 分支，不增加路径或字段。完整命中设计 §8.3 枚举短句时返回 `task_type=chitchat`、空 sources/usage/tool_calls，并记录 `route_intent → generate_chitchat_response`；其余及分类异常返回 `knowledge_qa`，记录 `route_intent → retrieve_active_faiss_chunks → generate_grounded_answer`。
- 阶段 5 真实问答样例必须使用 `mock=false`；阶段 1 stub 样例保留 `mock=true` 并标注为历史占位样例。`usage` 可以为 `null`，不得伪造 token 或费用。
- 同一 `X-Request-Id` 重试必须重放首次持久化结果；RUNNING 为 HTTP 409/code 2002；Python 不可达、超时、契约违约分别为 3001/3002/3003；收尾失败或超时回收为 HTTP 500/code 5000。
- V4 的 `answer_snapshot` 保存公共 `ChatMessageResponse.data` 的 camelCase 完整结构，版本 1 必须含 `answer`、`sources`、`taskType`、`runId`、`traceId`、`usage`、`executionTrace`、`mock`。成功重放只反序列化该快照，不重新调用 Python，也不从 assistant 内容重新拼装。
- 阶段 5 的事务顺序固定为“提交用户 message=RUNNING → 调 Python → 收尾事务写 assistant/快照/成功 qa_log 并置 SUCCEEDED”。Python 调用不得位于持有 RUNNING 行锁的长事务内；失败状态和错误 message 必须先安全归类再持久化。
- Java 从 MySQL 固定历史快照中选择按 message_id 升序的最近连续消息后缀，最多 20 条；预算为每条 UTF-8 正文字节数加 64 字节固定开销，总计最多 8192 字节。单条消息不截断；如果最新一条放不下则不发送 history。Python 将这些历史作为上下文注入模型提示词；history 不是事实来源，也不能覆盖系统规则。内部契约对超出条数/预算的请求返回 422，由 Java 映射为 502/3003。
- 消息请求生命周期由 `StageTwoMessageServiceImpl` 编排；切片 3 的 RUNNING-only 诊断 Controller/DTO 和旧 Gate/Preparation/Runtime/Terminal 服务链已移除，避免旁路只创建 RUNNING 而不完成请求。
- Java 定时回收器每 60 秒使用 V4 `(request_state, update_time)` 索引扫描超过 900 秒的 RUNNING 用户请求，在短事务中锁行并仅执行 RUNNING→FAILED，保存 HTTP 500/code 5000 和安全错误消息。RUNNING 行的 `update_time` 只用于超时筛选，不推导任何 `finishedAt`；Python 调用期间不持有锁，晚返回的执行结果若发现状态已被回收，不得覆盖 FAILED。
- V4 迁移前必须检查已有 `message.request_id`。有 assistant 的旧请求回填为成功快照，没有 assistant 的旧请求回填为 FAILED/5000；两者都禁止再次调用模型。
- 阶段 5 进入前置条件：至少一份正式授权文档已完成上传、解析、active chunk 和正式 FAISS manifest/readiness 对账，legacy 索引不得混入。

阶段 5 / 切片 3曾临时增加 `POST /api/chat/message-preparations` 诊断入口，以单独验证 RUNNING 闸门；切片 4完成正式生命周期后，该入口、DTO 与专属服务链已按用户授权删除，不再是当前运行接口。唯一正式同步问答入口为受 USER JWT 保护的 `/api/chat/messages`，它在 Python 调用前提交 RUNNING，并负责完整成功/失败收尾和重放。

## 阶段 6 / 切片 4 Python run 内存诊断契约

阶段 6 的 Python 单 worker 进程提供三条仅限内部开发诊断的只读接口：`GET /api/agent/run/{run_id}`、`GET /api/agent/run/{run_id}/steps`、`GET /api/agent/run/{run_id}/tool-calls`。它们都要求 `X-Internal-Token`，`run_id` 必须是 UUID；成功响应使用 snake_case，并复用同步 `execution_trace` 的 `TraceStep` 与 `TraceToolCall` schema。

同步 `POST /api/ask` 创建 `AgentState` 后先保存 RUNNING 快照，执行结束或失败后再保存终态快照。run 概要只返回 request/run/trace/conversation/user 标识、task_type 和状态；步骤与工具接口分别返回对应轨迹，不返回完整问题、Prompt、文档正文或模型回答。tool-call 的输入输出继续使用 ToolRegistry 已脱敏的审计字段。

该状态只存在于当前 Python 进程内，服务重启即丢失，不写 MySQL 或 Redis，也不替代 Java `agent_run`、`agent_step`、`tool_call` 审计表。Java 管理端仍只读取 Java 审计库；这三条接口不对浏览器公开。当前进程不存在该 run 时返回 404，Token 缺失/错误返回 401，Token 未配置返回 500，非法 UUID 路径返回 422。

## 阶段 4.1 内部文档生命周期契约

本节冻结 Java → Python 的最小文档解析边界。阶段 4 / 切片 4 已接入 `/api/parse` 路由、Java 内部客户端和后台状态调度；阶段 4 / 切片 5 已实现 local/OSS 原文件只读、SHA-256 复核、服务端格式复核和 PDF/DOCX/TXT/Markdown 文本提取；阶段 4 / 切片 6 已实现递归字符切分和 `knowledge_chunk` 批次持久化；阶段 4 / 切片 7 已接入本地 embedding、FAISS 临时构建、manifest 校验和活动索引原子切换。

阶段 4 / 切片 5 的运行边界：

- Word 明确指 `.docx`；旧二进制 `.doc` 没有受支持的 Python 解析依赖，Java 上传白名单会直接拒绝；
- local 模式读取 `UPLOAD_ROOT/OSS_KEY_PREFIX/storage_key`，最终解析路径必须仍位于 `UPLOAD_ROOT`；
- OSS 模式只使用 Head/Get，Python 凭据仍应限定 Bucket/Prefix 只读权限；
- Python 重新计算上传字节的 SHA-256，并在解析前验证扩展名与实际字节格式一致；
- API 日志只记录 doc_id、格式、文本长度、单元数量和 trace_id，不记录正文。
- 默认使用 `KNOWLEDGE_CHUNK_SIZE=800`、`KNOWLEDGE_CHUNK_OVERLAP=120`，分隔符顺序为段落、换行、空格、字符；参数可通过环境变量调整，但 overlap 必须小于 chunk size。
- Python 在一个 MySQL 事务中将同一 doc_id 的旧 active 切片置为 inactive，再插入新的 UUID `batch_id`；插入失败回滚，不留下半批次数据。

### POST `/api/parse`

Java 在后台任务中调用 Python 时发送 `X-Internal-Token`、`X-Trace-Id` 和以下 JSON。`X-Trace-Id` 必须等于请求体中的 `trace_id`。

```json
{
  "doc_id": 46,
  "storage_key": "2026/09/8d914a68-acde-4ceb-91b5-document.pdf",
  "content_hash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "force": false,
  "trace_id": "15fcdb04-b282-4c39-a51d-4fb7f948b43c"
}
```

约束：

- `doc_id` 必须是正整数；
- `storage_key` 是不含 `OSS_KEY_PREFIX` 的 OSS object key 相对部分，只能是相对路径，禁止绝对路径、反斜杠和 `..`；实际 object key 由 Java/Python 按统一 Prefix 规则拼接。
- `content_hash` 是上传字节的 64 位小写 SHA-256；
- OSS 模式下 Python 根据 `storage_key` 从 OSS 读取对象；只有 local 模式才在受限的 `UPLOAD_ROOT` 内解析，不能接收宿主机绝对路径；
- `force` 由 Java 根据重试语义决定，不能让 Python 自行改变 Java 的文档状态。

响应字段：

```json
{
  "doc_id": 46,
  "status": "COMPLETED",
  "batch_id": "4d7f1b54-9e9f-4f76-bd2a-4db0d5e1134a",
  "chunk_count": 12,
  "index_build_id": "c6e0f85a-4a4c-4e55-a5ca-0f8f0d4ac5b8",
  "trace_id": "15fcdb04-b282-4c39-a51d-4fb7f948b43c",
  "error_message": null
}
```

`status` 只能是 `COMPLETED` 或 `FAILED`。索引构建和 manifest 校验成功后返回 `COMPLETED`、非空 `batch_id`、实际 `chunk_count` 和 `index_build_id`；embedding、FAISS 写入、manifest 校验或原子激活失败时返回 `FAILED`，并保留上一个可用索引、恢复旧 active 批次、清理未激活构建。Java 负责把原因写入 `knowledge_doc.error_message` 并决定是否重试。`batch_id` 和 `index_build_id` 在失败时可以为 `null`，但批次已写入后失败响应会返回该 `batch_id`。

切片 7 的内部索引不把 `index_build_id` 写入 MySQL：FAISS 每个构建写入独立版本目录，`index_manifest.json` 保存 `schema_version`、embedding 模型、维度、归一化标记、active 切片数量、active 切片集合摘要、`index_build_id` 和 UTC `created_at`；`active.pointer` 通过临时文件替换原子切换。索引构建失败时不发布半成品。

### POST `/api/delete`

删除请求只传 Java 生成的文档 ID 和 trace ID：

```json
{
  "doc_id": 46,
  "trace_id": "15fcdb04-b282-4c39-a51d-4fb7f948b43c"
}
```

响应：

```json
{
  "doc_id": 46,
  "status": "DELETED",
  "deleted_chunk_count": 12,
  "trace_id": "15fcdb04-b282-4c39-a51d-4fb7f948b43c",
  "error_message": null
}
```

删除必须幂等；已经不存在的 chunk/index 不能被当作异常重复删除。Python 只负责派生切片和索引，Java 仍是 `knowledge_doc` 元数据及状态的唯一负责方。

错误语义：

| 场景 | HTTP |
| --- | ---: |
| 请求字段或 trace header 不合法 | 400 |
| 请求携带的内部 Token 缺失或错误 | 401 |
| Python 服务未配置内部 Token | 500（Java 公共边界映射为 5000） |
| `storage_key` 对应的 OSS object 不存在 | 404（仅 parse） |
| 与当前文档生命周期操作冲突 | 409 |
| 文件或请求体超过允许大小 | 413 |
| 服务端文件类型探测失败或文件类型不在白名单 | 415 |
| SHA-256 不一致、正文为空或文件无法解析 | HTTP 200，响应 `status=FAILED` 并返回非敏感原因 |
| Python 未就绪 | 503 |

### GET `/api/vector-store/stats`

该内部接口只读当前正式 FAISS 索引的 manifest、向量数量和 MySQL active chunk 对账结果，不触发索引重建、激活、删除或任何数据库/Redis 写入。调用必须携带 `X-Internal-Token` 与 UUID 格式的 `X-Trace-Id`；bodyless 请求只在响应中回显 trace ID。

一致且可服务时返回 HTTP 200；manifest 缺失、与 active chunks/provider 不一致或依赖不可用时返回 HTTP 503，响应仍使用相同字段结构并将 `ready` 置为 `false`。内部 Token 缺失/错误返回 401；trace header 缺失或不是 UUID 返回 400。

响应字段固定为：

```json
{
  "backend": "faiss",
  "index_build_id": "c6e0f85a-4a4c-4e55-a5ca-0f8f0d4ac5b8",
  "embedding_model": "BAAI/bge-small-zh-v1.5",
  "dimension": 512,
  "normalized": true,
  "chunk_count": 12,
  "active_chunk_digest": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "created_at": "2026-10-15T02:00:00Z",
  "ready": true,
  "trace_id": "15fcdb04-b282-4c39-a51d-4fb7f948b43c"
}
```

### POST `/api/vector-store/rebuild`

该内部接口强制根据当前 MySQL `knowledge_chunk.active=1` 的切片重建正式 FAISS 索引。请求不携带 body，只需要 `X-Internal-Token` 和 UUID 格式的 `X-Trace-Id`。每次成功调用都会生成新的 `index_build_id`，并在 manifest 校验通过后原子切换 `active.pointer`；旧 active build 在切换前保持可用。

成功返回 HTTP 200，响应复用 `VectorStoreStatsResponse` 且 `ready=true`。读取 active chunks、embedding、FAISS 写入或 manifest 校验失败时返回 HTTP 503，响应仍使用相同字段结构并将 `ready=false`；失败不会修改 MySQL active chunks，也不会切换旧 pointer。内部 Token 错误返回 401，trace header 缺失或非法返回 400。

## 阶段 3.5 消息反馈契约

### PUT `/api/chat/messages/{messageId}/feedback`

在 `contracts/public-openapi.yaml` 中，路径键为 `/chat/messages/{messageId}/feedback`，因为公共契约的 `servers` 已声明 `/api` 前缀。接口只允许 `ROLE_USER` 的已登录用户操作自己会话中的 assistant 消息。

请求体：

```json
{
  "value": "up"
}
```

`value` 只能是 `up` 或 `down`。同一用户对同一条 assistant 消息重复提交时覆盖旧值，不返回 409；第一版不支持取消反馈。

成功响应使用完整的 `Message` 资源，`data.feedback` 为本次提交后的值：

```json
{
  "code": 1,
  "msg": "success",
  "data": {
    "id": 901,
    "conversationId": 42,
    "role": "assistant",
    "content": "这是基于当前知识库生成的回答。",
    "createdAt": "2026-10-02T10:00:00Z",
    "feedback": "up",
    "mock": false
  }
}
```

`GET /api/chat/messages` 返回的每条 `Message` 都包含当前登录用户视角的 `feedback`：未反馈为 `null`，已反馈为 `up` 或 `down`；不返回全局聚合值。

错误语义：

| 场景 | HTTP | Result.code |
| --- | ---: | ---: |
| 未登录或 access token 无效 | 401 | 1001 |
| `messageId` 不存在 | 404 | 2001 |
| `messageId` 属于他人会话 | 403 | 1003 |
| `messageId` 是 user 消息 | 409 | 2002 |
| `value` 不是 `up` 或 `down` | 400 | 4000 |

## 命名与安全

- 浏览器与 Java 使用 camelCase；Java 与 Python 使用 snake_case。
- 业务 ID 使用 int64；requestId、traceId、runId、stepId 和 toolCallId 使用 UUID。
- 跨服务时间使用 UTC ISO 8601，前端显示时转换为 Asia/Shanghai。
- 浏览器只访问同源 `/api`，不得直连 Python。
- Java 调用 Python 业务接口必须发送 `X-Internal-Token` 和 `X-Trace-Id`。
- 同步消息请求必须发送 UUID 格式的 `X-Request-Id`；同一个重试必须复用同一个值。
- refresh token 只通过同源 HttpOnly Cookie 传递，不进入 JSON 或浏览器存储。

## Result 语义

Java 公共 JSON 使用：

```json
{
  "code": 1,
  "msg": "success",
  "data": {}
}
```

HTTP 状态表达传输和权限语义；`code` 表达稳定业务错误。不得使用 HTTP 200 包装认证、权限、参数、限流或服务器错误。
Java 侧 `ApiExceptionHandler` 已补齐 `MaxUploadSizeExceededException → 413`、类型探测失败 → 415，以及 `HandlerMethodValidationException` / `NoResourceFoundException` 的映射；对应 IMP-008 已关闭，后续只需按各切片的真实入口继续验证。
